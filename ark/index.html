Components

Five pillars, one architecture

Start with one component and grow into the full architecture. Onboard progressively — deploy Station today, add Wallet tomorrow, join the Mesh when ready. Every step adds value, and the full Ark is greater than the sum of its parts.

□

Station

Electron desktop application. Your verification station, credential vault, and mesh network node.

  • Document verification with OCR and census
  • Encrypted local vault with AES-256-GCM
  • Digital Signature (PKCS#11) and electronic signature
  • Every installation is a network node
◇

Wallet

Mobile PWA at mobile.attestto.com. Capture documents, biometric liveness proof, and verifiable credentials wallet.

  • Document capture with phone camera
  • Selfie with blink detection (liveness proof)
  • Verifiable credentials in your pocket
  • Direct connection to desktop via local WiFi
⊙

Mesh

Encrypted P2P network over libp2p. State synchronization between local devices and national nodes without a central server.

  • Blind Courier principle — nodes can't read the data they carry
  • ~120 KB per citizen
  • Works offline, syncs when connected
  • Cryptographic anchoring on Solana
⚙

Ceremony

Sovereign appliance for CA key ceremonies. Air-gapped Linux laptop, Shamir share distribution via local mesh.

  • Clean Linux laptop (live USB)
  • Key is split, original is destroyed
  • vLEI verification of shareholders
  • PKCS#11 support per jurisdiction
☍

Trust

CA trust framework with Shamir shareholders, on-chain transparency on Solana, and governance distributed across institutions.

  • CA key split: 2-of-3 today, 3-of-5 with MICITT/BCCR
  • Trust root at ca.attestto.sol
  • Auditable blockchain transparency
  • No actor has unilateral control
How it works

Desktop to mobile verification

Desktop and phone work together over local WiFi. Images and biometric data never leave your network — the connection is direct, no servers or cloud.

1

Open Station on your desktop

Select the document type to verify. Station generates a unique session QR code.

2

Scan the QR with your phone

The QR opens mobile.attestto.com with the WebSocket connection preconfigured. Your phone connects directly to your desktop.

3

Capture document and selfie

Front, back of document, and selfie with liveness proof (blink detection). Everything transmits in real-time to the desktop.

4

Automatic processing

Station runs OCR, extracts MRZ data, queries the TSE Census, validates the name, and generates the verifiable credential.

5

Credential in your vault

The credential is stored encrypted in the local vault. Sign it with Digital Signature, anchor it on Solana, or share it via verifiable presentation.

The connection between desktop and mobile is direct over local WiFi. No intermediary servers, no cloud, no internet dependency.

CA Governance

Distributed trust, not centralized

The Certificate Authority private key is split using Shamir's Secret Sharing. No individual actor — including Attestto — can sign unilaterally.

⋆

Shamir's Secret Sharing

The CA Ed25519 key is generated in an air-gapped ceremony and split into N shares. A threshold K is required to reconstruct it. The original key is destroyed.

Phase 1 (current): 2-of-3 internal
Phase 2: 3-of-5 with institutional partners
Phase 3: 5-of-9 multi-institutional
⚖

Institutional shareholders

Shareholders are verified representatives of institutions. Each holds a share that, alone, is useless. Only when the threshold gathers can the key be temporarily reconstructed.

Attestto — Technical operator (current)
Government — Regulatory body (proposed)
Central Bank — Financial authority (proposed)
♦

On-chain transparency

The CA public key is anchored at ca.attestto.sol on Solana. Every certificate issuance is recorded on the blockchain — auditable by anyone, at any time.

Root: ca.attestto.sol
Record: Each CA signature → Solana txn
Verification: Public and open

vLEI Verification

Before participating in a ceremony, each shareholder must have a verified LEI (Legal Entity Identifier) and a vLEI issued by GLEIF. This ensures they legitimately represent their institution.

Pre-requisite: Active LEI + issued vLEI
Verification: On-chain via vLEI-Solana-Bridge
Standard: GLEIF + ISO 17442
Key Ceremony

Sovereign, air-gapped, verifiable

The CA key generation ceremony occurs in a completely isolated environment. No internet connection. The only network is an encrypted local mesh between shareholder devices.

⚓

The sovereign appliance

A clean Linux laptop boots from live USB. No hard drive, no history, no external network. The ceremony software creates a private WiFi mesh to distribute Shamir shares to shareholder devices.

  • Linux live USB — no hard drive
  • Local WiFi mesh — no internet
  • Generate Ed25519 key pair
  • Split into Shamir shares
  • Destroy original key
  • Auditable, filmed ceremony
↺

Ceremony types

The system supports different ceremonies according to the CA lifecycle.

Genesis: First CA key generation
Rotation: Re-split with new shareholders
Signing: Reconstruct to sign certificates
Revocation: Revoke compromised key
☽

Multi-jurisdiction

Each country has its own electronic signature scheme. The appliance supports PKCS#11 to integrate with local signing hardware.

Costa Rica: Firma Digital (SINPE/BCCR)
Brazil: ICP-Brasil (ITI)
Mexico: e.firma (SAT)
Decentralized TLS

Four paths to the sovereign web

The ultimate goal: TLS certificates issued by Attestto CA recognized natively by browsers. Four parallel paths, each with a different time horizon.

Now

Browser extension

The Attestto ID extension intercepts TLS connections and validates certificates against ca.attestto.sol. Works today, no DNS infrastructure changes.

6 months

DANE / TLSA

Publish TLSA records in DNS pointing to Attestto CA certificates. Requires the domain to use DNSSEC. DANE validators already exist in some browsers.

12 months

Verification proxy

A transparent proxy that presents a Let's Encrypt certificate to the browser and an Attestto CA certificate to the destination server. Bridge between traditional and decentralized CA worlds.

2-5 years

W3C / IETF Standards

Participate in standards working groups so browsers natively recognize CA roots anchored in decentralized registries (blockchain, IPNS, SNS).
